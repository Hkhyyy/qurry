# Safety

English | [한국어](ko/safety.md)

- **Read-only data sources** are enforced by the engine, not only the UI: in every console, the table editor, Redis and exports, only reading statements run (plus transaction control and `SET`, but not switching read-only off).
- **Transactions**: a transaction you open (Manual mode, or `BEGIN` in Auto mode) is never committed or rolled back behind your back by result paging. Switching Manual → Auto with uncommitted changes asks first, and closing a tab, disconnecting, switching database or quitting with uncommitted changes asks before rolling them back. Data sources with open transactions are not auto-disconnected. In Manual mode any statement other than `SHOW` / `SET` / `USE` opens the transaction, a `SELECT` too (it may lock rows with `FOR UPDATE`, or call a function that writes), so Commit / Roll back show up after it on MySQL as on PostgreSQL. On MySQL that is also true of a statement that fails, since the server keeps the transaction open (with the row locks it took, or what a procedure changed before it failed). MySQL commits the open transaction by itself before DDL (not on temporary tables), `LOCK TABLES`, `BEGIN`, table maintenance (`ANALYZE TABLE`, `OPTIMIZE` …), account and plugin statements (`SET PASSWORD`, `INSTALL PLUGIN` …) and `SET autocommit = 1` when autocommit was off, but not for statements on temporary tables, MariaDB's `ANALYZE SELECT` / `ANALYZE UPDATE` …, `SET autocommit = 1` when it was already on, or `UNLOCK TABLES` after `BEGIN` (which already released the locks). Qurry doesn't guess from the words: in an open transaction (and in MySQL Manual mode), after any statement other than a `SELECT` or a row change (`INSERT`, `UPDATE`, `DELETE` …), it asks the server whether the transaction is still open (in a way that changes nothing, so a pending `SET TRANSACTION ISOLATION LEVEL …` still applies to the next transaction), and if it was committed the Production log records "COMMIT (implicit)". It does the same after such a statement fails: DDL, `LOCK TABLES`, `SET PASSWORD`, `ALTER USER` and `INSTALL PLUGIN` often commit it even when they then fail (a duplicate column, a missing table or user, a missing plugin file), but not when they fail before that (a syntax error, a name that is too long, no database selected), and the error doesn't tell which. If it was committed, the console says so (in the error, or in a warning when the statement ran) and Roll back can no longer undo the earlier changes (on a Production data source, the Production log has their undo SQL where it could keep it). A `CALL` (or `EXECUTE` of a prepared statement, or a MariaDB `BEGIN NOT ATOMIC … END` block, which is not a `BEGIN`; a `BEGIN` followed by a comment still is) can commit or roll back the transaction inside it, and a DDL that times out or deadlocks on its metadata lock (1205 / 1213) has already committed it, while a deadlock in a `SET` rolls it back: when the transaction ended in one of these, the server's answer doesn't tell which, so the console says so and asks you to check the data, and the Production log records "ENDED (committed or rolled back)", shown as of unknown outcome. In Auto mode outside a transaction it asks after a `CALL`, `EXECUTE` or `BEGIN NOT ATOMIC` block too, since a procedure that starts a transaction and doesn't commit leaves it open: the console then shows it open, with Commit / Roll back. If the server can't answer (MySQL 5.6, or a MySQL-compatible server such as TiDB that accepts the question inside a transaction, which Qurry checks when the console connects), Qurry keeps the transaction shown as open; after a DDL there, press Commit to close it (it saves nothing more). On MySQL 5.7 and later, asking replaces the statement's warnings: `SHOW WARNINGS` right after such a statement in an open transaction shows error 1766 (session_track_gtids), not the statement's own warnings. To see those (e.g. whether an `ALTER TABLE` truncated data), run the statement in Auto mode outside a transaction, where Qurry doesn't ask (except after a `CALL` or `EXECUTE`, whose warnings the console can't show).
- **Production transactions** (#106): on a Production data source new consoles start in Tx: Manual, so a change stays pending until you Commit or Roll back (Data Source Properties › Options › **Production: start consoles in Manual transaction mode**, on by default; TUI: the data source form's `Production Manual`; off, consoles start in the Transaction control mode). Only PostgreSQL and MySQL consoles can be in Manual: Redis and driver plugin consoles start in Auto. On Production a plain read (one that takes no row locks and calls no side-effect function, as Production's confirmation decides it) run before the first change doesn't open the transaction: it runs as in Auto, in a transaction of its own that ends with it, so reading holds no snapshot or table locks on the server (an `ALTER TABLE` or a migration doesn't wait behind it, nor do the queries behind that) and nothing shows as pending. The transaction opens at the first other statement (a change, `SELECT … FOR UPDATE`), or at a `BEGIN` you type when you want several reads to see one snapshot. Such a read runs read-only, so a function in it that writes is refused (nothing is changed or committed), and the error says to run `BEGIN` first. The first such console of a data source says so once in Output (TUI: also the status line), with where to turn it off. A console with an open transaction shows **● Transaction pending** beside Commit / Roll back, red on Production (TUI: its title says "pending" with the Commit and Roll back keys); Commit / Roll back also show for a `BEGIN` typed in Auto mode. Closing the tab, switching the database, disconnecting or quitting asks first, as for any open transaction. A Production transaction left without a statement for 5 minutes is reminded about once (Output, the badge's hover and the status bar), saying that its changes aren't saved and the rows it changed stay locked (or, when nothing was changed in it, that it still keeps the locks of what ran in it), and the server's own limit when it has one — left out when keep-alive pings sooner, since the ping restarts that limit's clock; a statement, Commit or Roll back starts the wait again. When the server ends a session that sat idle in a transaction (PostgreSQL `idle_in_transaction_session_timeout`, MySQL `wait_timeout`), the next statement or Commit says so by the setting's name, that the transaction was rolled back and nothing more was sent, and the Production log records "ROLLBACK (by the server)" (a Commit there is not of unknown outcome: the server never got it). A keep-alive query (Options) counts as a statement for PostgreSQL's limit and MySQL's `wait_timeout`. MCP's writes (`execute` with `--allow-write`) never use a console: each still runs in a transaction of its own and commits.
- **Loading more after a reconnect**: saving a data source's settings, disconnecting it or the idle auto-disconnect closes its consoles' connections. Scrolling an open result (console or table tab) on then reopens its statement on a new connection after the rows already shown, in the schema it ran in (PostgreSQL `search_path`, MySQL `USE`), as when a result unused for a minute is reopened. Without `ORDER BY` the server decides the order, and rows changed in between can be skipped or shown twice. It is not reopened when the data source now points at another server or database (host, port, user, type, tunnel or database changed, or SSL lowered) or runs other settings first (startup script, time zone or isolation level changed), when the result was read in a transaction (Manual mode or `BEGIN`), which ended with the old connection, when Qurry couldn't read which schema it ran in, or when the statement isn't a plain read (it calls a function with side effects such as `nextval`, `pg_sleep`, `pg_notify` or `get_lock`, or locks rows with `FOR UPDATE`, `FOR SHARE`, `FOR KEY SHARE` or `LOCK IN SHARE MODE`, …): the grid keeps "Couldn't load more rows: …" with the reason (GUI: beside the row count in its toolbar, with **Run again**; TUI: on its bottom edge) and the status bar says it too, its row count keeps the `+`, and running the query again loads it from the start. Rows that arrive after the tab ran again are dropped, and a load-more asked while the tab runs again is not answered with the new result's rows. Read-only data sources check the statement again before it is reopened.
- **Confirmations** before `UPDATE`/`DELETE` without `WHERE`, `DROP`, `TRUNCATE` and Redis `FLUSHALL`/`FLUSHDB`/`DEL` (GUI and TUI, the Redis Terminal too, where Production also asks before any write).
- **Production data sources** show how many rows a changing statement will touch and ask before running it ([Data sources](data-sources.md)). The question comes up once the rows are counted, so in the TUI it doesn't take keys you typed on meanwhile: `y` / `Enter` answer it only after a pause (each key starts the wait again; `n` / `Esc` cancel at once), and while you are typing in another dialog it waits until you close that one. The same goes for the other questions that open on their own (driver download, migrations, test data, copied rows) and for a question a notice was covering. A yes runs the statements in the console that asked, shown again, even if you switched to another tab meanwhile; if that console was closed, nothing runs.
- **Grid edits on Production** (a table tab, or a console result): Submit lists the statements and asks before saving them (each `UPDATE` / `DELETE` must change exactly one row, or nothing is saved). In Auto mode grid edits are saved on a separate connection, not the console's session, so `SET ROLE`, session settings and temporary tables in the console don't apply to them; results of a temporary table or a locking read (`FOR UPDATE`, `LOCK IN SHARE MODE` …) stay read-only for that reason. In Manual mode or with a transaction open, Submit runs the edits in the console's transaction (the question says so), under a savepoint: one that fails or doesn't change exactly one row undoes only that Submit, and the transaction goes on. They stay pending until Commit / Roll back, and the Production log has them as not committed, with their undo SQL.
- **Editing a join's result** (#102): a column of a join is edited in its own table when that is a base table (not a view, a materialized or foreign table, or a temporary table) whose whole primary key is in the result. Each edited row and table becomes its own `UPDATE <table> SET … WHERE <key> = …`, with the key values as the row was read, through the same Submit (exactly one row each, read-only data sources refused, the Production question and log). Every other column is read-only, and says why: the GUI dims its header with 🔒 and shows the reason on hover (on the cell, for a row-only reason), the TUI's status line says it on an edit key ("Read-only: the result doesn't include the primary key of public.users (idx).", "… is computed …"). In an outer join, a table's cells in a row where no row of it matched (its key is NULL there) are read-only. A table joined with itself is edited per occurrence, each by its own key columns, so select both occurrences' keys as `alias.column`; where Qurry can't tell which occurrence a column is, it stays read-only with that reason. Columns with the same name in two tables (`idx`, `status`) go to their own table: PostgreSQL says where each result column comes from (its table and column number), and MySQL, which doesn't through the driver, has its select list lined up with each table's columns and the names the server returned (a bare `*` over a join with `USING` or `NATURAL` stays read-only there, since the merged columns come once; use `alias.*`). Rows can't be added, cloned or deleted in a join's result, since a row isn't one table's.
- **Production log**: every changing statement run on a Production data source (console, table editor, test data, copies) is recorded with its time, data source, affected rows and whether it was still uncommitted; later COMMIT / ROLLBACK are recorded too. A change is written to the log before it runs, so it is there even if Qurry stops while it runs; if the log can't be written (disk full, no permission on the file or the config folder), the change and the COMMIT of logged changes are not run, and the message says what to fix — then run it again (a rollback always runs). If a change ran but its result couldn't be written, you get a warning, not an error: it did run, so don't run it again. The log shows such an entry as "no result recorded", as it does for a change that is still running or was cut off when Qurry stopped. When the server ends a transaction with logged changes without a COMMIT (a deadlock, a failed COMMIT, a lost connection), the log records "ROLLBACK (by the server)". On PostgreSQL a failed statement aborts the transaction, and a COMMIT then only rolls it back: Qurry says "Not committed", and the log records the COMMIT as failed followed by "ROLLBACK (by the server)" (run the changes again without the failing statement; `ROLLBACK TO SAVEPOINT` before the COMMIT keeps the rest). It records "ROLLBACK (disconnected)" when you disconnect (or change the data source's settings) with them open. If the connection is lost during the COMMIT itself, the server may have committed before it went: the log records "COMMIT outcome unknown (connection lost)", the Commit button's notice is titled "Commit outcome unknown" (not "Commit failed"), and you should check the data before you run the changes again. Older Qurry versions list each Production change twice (once before it ran, once with its result), so update the TUI (e.g. Homebrew) together with the app. GUI: `⇧⌘A` › Production Log… · TUI: `⌃k` › Production Log…. It is kept in the config folder (`audit.jsonl`, readable only by you, the latest 2,000 entries).
- **Undo SQL**: just before a simple `UPDATE` / `DELETE` on one table runs on a Production data source (PostgreSQL, MySQL), the rows it will change are saved (up to 1,000 rows), and the log keeps SQL that puts them back. They are read in the statement's own transaction and locked (`SELECT … FOR UPDATE`), so another session can't change them in between: in Auto mode the statement then commits right away, as before; in a transaction you opened (Manual, or `BEGIN`) both join it. On PostgreSQL an `UPDATE` takes the lock the `UPDATE` itself takes (`FOR NO KEY UPDATE`), so it doesn't hold up other sessions inserting child rows; a role without the `UPDATE` privilege (e.g. only `SELECT` and `DELETE`) can't lock rows, and its rows are read without the lock. If you cancel the statement, or the server stops waiting for the rows (timeout, deadlock), it is not run at all. On MySQL a deadlock rolls back your whole open transaction: the message then says the earlier uncommitted changes are lost. It is never run for you: open it in a console from the log, check it, and run it (it goes through the Production confirmation again). No undo is kept when the table has no primary key, the statement changes the primary key, or it changed more rows than were saved right before it (rows that started to match while it ran, row-level security that hides rows from a locking read, triggers).
- **Explain Analyze** really runs the statement. On PostgreSQL and MySQL it runs inside a transaction that is rolled back — every statement, reads included, since a function a `SELECT` calls can write — so its table changes are undone (on MySQL only in transactional tables (InnoDB); a MyISAM or MEMORY table keeps the change). On other data sources it isn't wrapped, and Qurry asks first for a statement that changes data ("it changes data"). A rollback can't undo what a statement does outside the transaction — sequence values (`nextval`, `setval`), `dblink_exec` on another server, files (`SELECT … INTO OUTFILE`), advisory locks, a consumed replication slot — nor, in a selection run as one statement, a `COMMIT` or MySQL DDL after the first statement (only the first is explained; the rest run as they are). For these Qurry asks first ("a rollback can't undo …"), and for an `UPDATE` or `DELETE` without `WHERE` (it changes every row and locks them until the rollback, which holds up other sessions writing to the table; a MyISAM or MEMORY table keeps the change). Run Anyway goes on, Cancel runs nothing; to see a plan without running anything, use Explain Plan. Output says afterwards what may stay. Qurry can't see inside a trigger or a function body, so for a write it says the table changes were undone but not what a trigger or function did outside the transaction, and it doesn't ask before a statement that calls a user-defined function: its table changes are rolled back too, but what it does outside the transaction (a sequence value, `dblink`) stays. For a function you don't know, use Explain Plan. The numbers an `INSERT` takes from a serial or `AUTO_INCREMENT` column are used up too; Qurry doesn't ask for that. Explain asks one question, not the "dangerous statement" question as well: Explain Analyze's question gives the `DELETE` without `WHERE` reason when there is one, and on a Production data source it replaces the row-count confirmation. When a transaction is open (Manual mode, a `BEGIN` you ran, the next transaction a `COMMIT AND CHAIN` or `ROLLBACK AND CHAIN` opens, on MySQL one Qurry didn't see open, such as a `START TRANSACTION` inside a `/*! … */` comment, or autocommit switched off any way: `SET autocommit = 0`, a procedure, a dump's `/*!40101 … */` header), Qurry wraps the statement in `SAVEPOINT` … `ROLLBACK TO SAVEPOINT`, so what you left uncommitted stays uncommitted (on MySQL a `BEGIN` would commit it) and is yours to Commit or Roll back. A read-only data source allows this too. GUI and TUI decide this the same way, with the same words.
- **Scripts in Auto mode** run statement by statement: if one fails, the output says how many earlier statements were already committed.
- **Table editor** saves all edits in one transaction, and each `UPDATE`/`DELETE` must change exactly one row, otherwise nothing is saved.
- **Import** of data source files shows what changes first (e.g. "turns Read-only OFF", "turns SSL OFF", a new server, new startup script).
- **MCP server** (AI tools): each data source is Off, Read or Read & write for MCP, new ones start Off and Production ones stay hidden until you turn them on ([MCP server](mcp.md)). The read-only checks are a second line of defence: give MCP its own **least-privilege database user** (a read-only role; no superuser, `FILE`, `pg_read_server_files`, `pg_signal_backend` or `dblink`), so a function the checks don't know about still can't do harm.
- **Saved passwords** are only sent to the server they were saved for: after changing the type, host, port, user or SSH tunnel, or turning SSL off, Test and Save ask for the password again, and importing another server under the same data source, or a file that turns on "Allow unencrypted connection", removes the saved password. Driver and embedding requests don't follow redirects, and your OpenAI key is only sent to OpenAI (or the server in `OPENAI_BASE_URL`), never to an index's own "OpenAI-compatible" server.
- **Unencrypted connections** are never a reflex on Production: after a connect error from a server without TLS, dev and LAN data sources offer a one-click **Allow unencrypted for this data source** (it says the password will be sent unencrypted to that host), but Production data sources don't — turning off encryption there is a choice you make in the data source form, with the setting in view, and the engine refuses the one-click path for them too. The confirm never takes a stray key: in the TUI only `y` answers it, and only after a pause (not Enter, and not a key typed while you are still typing: each key starts the wait again; `n` / `Esc` cancel at once). A console never re-runs the statement after it; it only reconnects ([Data sources](data-sources.md)).
- **Query history** (GUI and TUI, the Redis Terminal's ↑↓ too) hides passwords in `CREATE/ALTER USER … PASSWORD '…'`, `IDENTIFIED BY '…'` and Redis `AUTH`, `HELLO … AUTH`, `CONFIG SET requirepass` / `masterauth`, `ACL SETUSER`'s `>password` / `#hash` rules and `MIGRATE … AUTH` / `AUTH2` (by argument, so a quoted password with spaces is hidden whole).
- **Releases** are built only from `main` (betas) and version tags on `main` (stable, see [Updates](updates.md#how-releases-are-made)) by GitHub Actions pinned to commit SHAs, with `SHA256SUMS` and build provenance attestations. The update signing key is used only in a separate signing step (never during the build). The GUI checks the update bundle's signature, and `qurry-tui --update` checks the signature of `SHA256SUMS` (same key) and then the checksum before installing.
