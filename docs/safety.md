# Safety

English | [한국어](ko/safety.md)

- **Read-only data sources** are enforced by the engine, not only the UI: in every console, the table editor, Redis and exports, only reading statements run (plus transaction control and `SET`, but not switching read-only off).
- **Transactions**: a transaction you open (Manual mode, or `BEGIN` in Auto mode) is never committed or rolled back behind your back by result paging. Switching Manual → Auto with uncommitted changes asks first, and closing a tab, disconnecting, switching database or quitting with uncommitted changes asks before rolling them back. Data sources with open transactions are not auto-disconnected.
- **Confirmations** before `UPDATE`/`DELETE` without `WHERE`, `DROP`, `TRUNCATE` and Redis `FLUSHALL`/`FLUSHDB`/`DEL` (GUI and TUI).
- **Production data sources** show how many rows a changing statement will touch and ask before running it ([Data sources](data-sources.md)).
- **Production log**: every changing statement run on a Production data source (console, table editor, test data, copies) is recorded with its time, data source, affected rows and whether it was still uncommitted; later COMMIT / ROLLBACK are recorded too. A change is written to the log before it runs, so it is there even if Qurry stops while it runs; if the log can't be written (disk full, no permission on the file or the config folder), the change and the COMMIT of logged changes are not run, and the message says what to fix — then run it again (a rollback always runs). If a change ran but its result couldn't be written, you get a warning, not an error: it did run, so don't run it again. The log shows such an entry as "no result recorded", as it does for a change that is still running or was cut off when Qurry stopped. When the server ends a transaction with logged changes without a COMMIT (a deadlock, a failed COMMIT, a lost connection), the log records "ROLLBACK (by the server)". Older Qurry versions list each Production change twice (once before it ran, once with its result), so update the TUI (e.g. Homebrew) together with the app. GUI: `⇧⌘A` › Production Log… · TUI: `⌃k` › Production Log…. It is kept in the config folder (`audit.jsonl`, readable only by you, the latest 2,000 entries).
- **Undo SQL**: just before a simple `UPDATE` / `DELETE` on one table runs on a Production data source (PostgreSQL, MySQL), the rows it will change are saved (up to 1,000 rows), and the log keeps SQL that puts them back. They are read in the statement's own transaction and locked (`SELECT … FOR UPDATE`), so another session can't change them in between: in Auto mode the statement then commits right away, as before; in a transaction you opened (Manual, or `BEGIN`) both join it. On PostgreSQL an `UPDATE` takes the lock the `UPDATE` itself takes (`FOR NO KEY UPDATE`), so it doesn't hold up other sessions inserting child rows; a role without the `UPDATE` privilege (e.g. only `SELECT` and `DELETE`) can't lock rows, and its rows are read without the lock. If you cancel the statement, or the server stops waiting for the rows (timeout, deadlock), it is not run at all. On MySQL a deadlock rolls back your whole open transaction: the message then says the earlier uncommitted changes are lost. It is never run for you: open it in a console from the log, check it, and run it (it goes through the Production confirmation again). No undo is kept when the table has no primary key, the statement changes the primary key, or it changed more rows than were saved right before it (rows that started to match while it ran, row-level security that hides rows from a locking read, triggers).
- **Explain Analyze** really runs the statement. On PostgreSQL and MySQL it runs inside a transaction that is rolled back — every statement, reads included, since a function a `SELECT` calls can write — so its table changes are undone (on MySQL only in transactional tables (InnoDB); a MyISAM or MEMORY table keeps the change). On other data sources it isn't wrapped, and Qurry asks first for a statement that changes data ("it changes data"). A rollback can't undo what a statement does outside the transaction — sequence values (`nextval`, `setval`), `dblink_exec` on another server, files (`SELECT … INTO OUTFILE`), advisory locks, a consumed replication slot — nor, in a selection run as one statement, a `COMMIT` or MySQL DDL after the first statement (only the first is explained; the rest run as they are). For these Qurry asks first ("a rollback can't undo …"), and also for a `SELECT` that calls a function it doesn't know (a user-defined one, or a built-in outside its list: "it calls f(), and a rollback can't undo what a function does outside the transaction"). Run Anyway goes on, Cancel runs nothing; to see a plan without running anything, use Explain Plan. Output says afterwards what may stay. Qurry can't see inside a trigger or a function body, so for a write it says the table changes were undone but not what a trigger or function did outside the transaction. The numbers an `INSERT` takes from a serial or `AUTO_INCREMENT` column are used up too; Qurry doesn't ask for that. The "dangerous statement" question (`DELETE` without `WHERE` …) isn't asked for Explain: Explain Analyze asks its own question when it needs one. GUI and TUI decide this the same way, with the same words.
- **Scripts in Auto mode** run statement by statement: if one fails, the output says how many earlier statements were already committed.
- **Table editor** saves all edits in one transaction, and each `UPDATE`/`DELETE` must change exactly one row, otherwise nothing is saved.
- **Import** of data source files shows what changes first (e.g. "turns Read-only OFF", "turns SSL OFF", a new server, new startup script).
- **MCP server** (AI tools): each data source is Off, Read or Read & write for MCP, new ones start Off and Production ones stay hidden until you turn them on ([MCP server](mcp.md)). The read-only checks are a second line of defence: give MCP its own **least-privilege database user** (a read-only role; no superuser, `FILE`, `pg_read_server_files`, `pg_signal_backend` or `dblink`), so a function the checks don't know about still can't do harm.
- **Saved passwords** are only sent to the server they were saved for: after changing the type, host, port, user or SSH tunnel, or turning SSL off, Test and Save ask for the password again, and importing another server under the same data source, or a file that turns on "Allow unencrypted connection", removes the saved password. Driver and embedding requests don't follow redirects, and your OpenAI key is only sent to OpenAI (or the server in `OPENAI_BASE_URL`), never to an index's own "OpenAI-compatible" server.
- **Query history** (GUI) hides passwords in `CREATE/ALTER USER … PASSWORD '…'`, `IDENTIFIED BY '…'` and Redis `AUTH`.
- **Releases** are built only from `main` (betas) and version tags on `main` (stable, see [Updates](updates.md#how-releases-are-made)) by GitHub Actions pinned to commit SHAs, with `SHA256SUMS` and build provenance attestations. The update signing key is used only in a separate signing step (never during the build). The GUI checks the update bundle's signature, and `qurry-tui --update` checks the signature of `SHA256SUMS` (same key) and then the checksum before installing.
