# Safety

English | [한국어](ko/safety.md)

- **Read-only data sources** are enforced by the engine, not only the UI: in every console, the table editor, Redis and exports, only reading statements run (plus transaction control and `SET`, but not switching read-only off).
- **Transactions**: a transaction you open (Manual mode, or `BEGIN` in Auto mode) is never committed or rolled back behind your back by result paging. Switching Manual → Auto with uncommitted changes asks first, and closing a tab, disconnecting, switching database or quitting with uncommitted changes asks before rolling them back. Data sources with open transactions are not auto-disconnected. In Manual mode any statement other than `SHOW` / `SET` / `USE` opens the transaction, a `SELECT` too (it may lock rows with `FOR UPDATE`, or call a function that writes), so Commit / Roll back show up after it on MySQL as on PostgreSQL. On MySQL that is also true of a statement that fails, since the server keeps the transaction open (with the row locks it took, or what a procedure changed before it failed). MySQL commits the open transaction by itself before DDL (not on temporary tables), `LOCK TABLES`, `BEGIN`, table maintenance (`ANALYZE TABLE`, `OPTIMIZE` …), account and plugin statements (`SET PASSWORD`, `INSTALL PLUGIN` …) and `SET autocommit = 1` when autocommit was off, but not for statements on temporary tables, MariaDB's `ANALYZE SELECT` / `ANALYZE UPDATE` …, `SET autocommit = 1` when it was already on, or `UNLOCK TABLES` after `BEGIN` (which already released the locks). Qurry doesn't guess from the words: in an open transaction (and in MySQL Manual mode), after any statement other than a `SELECT` or a row change (`INSERT`, `UPDATE`, `DELETE` …), it asks the server whether the transaction is still open (in a way that changes nothing, so a pending `SET TRANSACTION ISOLATION LEVEL …` still applies to the next transaction), and if it was committed the Production log records "COMMIT (implicit)". It does the same after such a statement fails: DDL, `LOCK TABLES`, `SET PASSWORD`, `ALTER USER` and `INSTALL PLUGIN` often commit it even when they then fail (a duplicate column, a missing table or user, a missing plugin file), but not when they fail before that (a syntax error, a name that is too long, no database selected), and the error doesn't tell which. If it was committed, the console says so (in the error, or in a warning when the statement ran) and Roll back can no longer undo the earlier changes (on a Production data source, the Production log has their undo SQL where it could keep it). A `CALL` (or `EXECUTE` of a prepared statement, or a MariaDB `BEGIN NOT ATOMIC … END` block, which is not a `BEGIN`) can commit or roll back the transaction inside it, and a DDL that times out or deadlocks on its metadata lock (1205 / 1213) has already committed it, while a deadlock in a `SET` rolls it back: when the transaction ended in one of these, the server's answer doesn't tell which, so the console says so and asks you to check the data, and the Production log records "ENDED (committed or rolled back)", shown as of unknown outcome. In Auto mode outside a transaction it asks after a `CALL`, `EXECUTE` or `BEGIN NOT ATOMIC` block too, since a procedure that starts a transaction and doesn't commit leaves it open: the console then shows it open, with Commit / Roll back. If the server can't answer (MySQL 5.6, or a MySQL-compatible server such as TiDB that accepts the question inside a transaction, which Qurry checks when the console connects), Qurry keeps the transaction shown as open; after a DDL there, press Commit to close it (it saves nothing more). On MySQL 5.7 and later, asking replaces the statement's warnings: `SHOW WARNINGS` right after such a statement in an open transaction shows error 1766 (session_track_gtids), not the statement's own warnings. To see those (e.g. whether an `ALTER TABLE` truncated data), run the statement in Auto mode outside a transaction, where Qurry doesn't ask (except after a `CALL` or `EXECUTE`, whose warnings the console can't show).
- **Confirmations** before `UPDATE`/`DELETE` without `WHERE`, `DROP`, `TRUNCATE` and Redis `FLUSHALL`/`FLUSHDB`/`DEL` (GUI and TUI).
- **Production data sources** show how many rows a changing statement will touch and ask before running it ([Data sources](data-sources.md)).
- **Production log**: every changing statement run on a Production data source (console, table editor, test data, copies) is recorded with its time, data source, affected rows and whether it was still uncommitted; later COMMIT / ROLLBACK are recorded too. A change is written to the log before it runs, so it is there even if Qurry stops while it runs; if the log can't be written (disk full, no permission on the file or the config folder), the change and the COMMIT of logged changes are not run, and the message says what to fix — then run it again (a rollback always runs). If a change ran but its result couldn't be written, you get a warning, not an error: it did run, so don't run it again. The log shows such an entry as "no result recorded", as it does for a change that is still running or was cut off when Qurry stopped. When the server ends a transaction with logged changes without a COMMIT (a deadlock, a failed COMMIT, a lost connection), the log records "ROLLBACK (by the server)". On PostgreSQL a failed statement aborts the transaction, and a COMMIT then only rolls it back: Qurry says "Not committed", and the log records the COMMIT as failed followed by "ROLLBACK (by the server)" (run the changes again without the failing statement; `ROLLBACK TO SAVEPOINT` before the COMMIT keeps the rest). It records "ROLLBACK (disconnected)" when you disconnect (or change the data source's settings) with them open. If the connection is lost during the COMMIT itself, the server may have committed before it went: the log records "COMMIT outcome unknown (connection lost)", the Commit button's notice is titled "Commit outcome unknown" (not "Commit failed"), and you should check the data before you run the changes again. Older Qurry versions list each Production change twice (once before it ran, once with its result), so update the TUI (e.g. Homebrew) together with the app. GUI: `⇧⌘A` › Production Log… · TUI: `⌃k` › Production Log…. It is kept in the config folder (`audit.jsonl`, readable only by you, the latest 2,000 entries).
- **Undo SQL**: just before a simple `UPDATE` / `DELETE` on one table runs on a Production data source (PostgreSQL, MySQL), the rows it will change are saved (up to 1,000 rows), and the log keeps SQL that puts them back. They are read in the statement's own transaction and locked (`SELECT … FOR UPDATE`), so another session can't change them in between: in Auto mode the statement then commits right away, as before; in a transaction you opened (Manual, or `BEGIN`) both join it. On PostgreSQL an `UPDATE` takes the lock the `UPDATE` itself takes (`FOR NO KEY UPDATE`), so it doesn't hold up other sessions inserting child rows; a role without the `UPDATE` privilege (e.g. only `SELECT` and `DELETE`) can't lock rows, and its rows are read without the lock. If you cancel the statement, or the server stops waiting for the rows (timeout, deadlock), it is not run at all. On MySQL a deadlock rolls back your whole open transaction: the message then says the earlier uncommitted changes are lost. It is never run for you: open it in a console from the log, check it, and run it (it goes through the Production confirmation again). No undo is kept when the table has no primary key, the statement changes the primary key, or it changed more rows than were saved right before it (rows that started to match while it ran, row-level security that hides rows from a locking read, triggers).
- **Explain Analyze** of a statement that changes data runs inside a transaction that is rolled back (PostgreSQL, MySQL), so it changes nothing.
- **Scripts in Auto mode** run statement by statement: if one fails, the output says how many earlier statements were already committed.
- **Table editor** saves all edits in one transaction, and each `UPDATE`/`DELETE` must change exactly one row, otherwise nothing is saved.
- **Import** of data source files shows what changes first (e.g. "turns Read-only OFF", "turns SSL OFF", a new server, new startup script).
- **MCP server** (AI tools): each data source is Off, Read or Read & write for MCP, new ones start Off and Production ones stay hidden until you turn them on ([MCP server](mcp.md)). The read-only checks are a second line of defence: give MCP its own **least-privilege database user** (a read-only role; no superuser, `FILE`, `pg_read_server_files`, `pg_signal_backend` or `dblink`), so a function the checks don't know about still can't do harm.
- **Saved passwords** are only sent to the server they were saved for: after changing the type, host, port, user or SSH tunnel, or turning SSL off, Test and Save ask for the password again, and importing another server under the same data source, or a file that turns on "Allow unencrypted connection", removes the saved password. Driver and embedding requests don't follow redirects, and your OpenAI key is only sent to OpenAI (or the server in `OPENAI_BASE_URL`), never to an index's own "OpenAI-compatible" server.
- **Query history** (GUI) hides passwords in `CREATE/ALTER USER … PASSWORD '…'`, `IDENTIFIED BY '…'` and Redis `AUTH`.
- **Releases** are built only from `main` by GitHub Actions pinned to commit SHAs, with `SHA256SUMS` and build provenance attestations. The update signing key is used only in a separate signing step (never during the build). The GUI checks the update bundle's signature, and `qurry-tui --update` checks the signature of `SHA256SUMS` (same key) and then the checksum before installing.
