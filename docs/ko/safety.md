# 안전장치

[English](../safety.md) | 한국어

- **읽기 전용 Data Source** 는 화면만이 아니라 엔진이 지킵니다: 모든 콘솔, 테이블 편집기, Redis, 내보내기에서 읽는 문장만 실행합니다 (트랜잭션 제어와 `SET` 은 되지만 읽기 전용을 끄는 것은 안 됨).
- **트랜잭션**: 직접 연 트랜잭션 (Manual 모드, 또는 Auto 모드의 `BEGIN`) 은 결과를 나눠 받는 동안 몰래 커밋되거나 되돌려지지 않습니다. 커밋 안 한 변경이 있을 때 Manual → Auto 로 바꾸면 먼저 묻고, 탭 닫기 · 연결 끊기 · 데이터베이스 바꾸기 · 종료도 되돌리기 전에 묻습니다. 열린 트랜잭션이 있는 Data Source 는 자동으로 연결이 끊기지 않습니다.
- **확인**: `WHERE` 없는 `UPDATE`/`DELETE`, `DROP`, `TRUNCATE`, Redis `FLUSHALL`/`FLUSHDB`/`DEL` 은 실행 전에 묻습니다 (GUI, TUI).
- **Production Data Source** 는 바꾸는 문장이 몇 행을 건드리는지 보여 주고 실행 전에 묻습니다 ([Data Source](data-sources.md)).
- **운영 작업 기록**: Production Data Source 에서 실행한 바꾸는 문장 (콘솔, 테이블 편집기, 테스트 데이터, 복사) 을 시각 · Data Source · 바뀐 행 수 · 커밋 전이었는지와 함께 남기고, 뒤의 COMMIT / ROLLBACK 도 남깁니다. 바꾸는 문장은 실행하기 전에 먼저 기록하므로, 실행 중에 Qurry 가 멈춰도 기록에 남습니다. 기록을 쓸 수 없으면 (디스크가 가득 참, 파일이나 설정 폴더에 쓰기 권한이 없음) 그 문장과, 기록된 변경의 COMMIT 은 실행하지 않고 무엇을 고치면 되는지 알려 줍니다. 고친 뒤 다시 실행하세요 (ROLLBACK 은 언제나 실행됩니다). 실행은 됐는데 결과를 기록하지 못하면 오류가 아니라 경고로 알려 줍니다: 이미 실행됐으니 다시 실행하지 마세요. 기록에는 "no result recorded" 로 보이며, 아직 실행 중이거나 Qurry 가 멈춰 끊긴 변경도 그렇게 보입니다. 기록된 변경이 있는 트랜잭션을 서버가 COMMIT 없이 끝내면 (교착 상태, 실패한 COMMIT, 끊긴 연결) "ROLLBACK (by the server)" 로 남깁니다. 이전 버전의 Qurry 는 Production 변경을 하나마다 두 번 (실행 전, 결과) 보여 주므로, TUI (Homebrew 등) 도 앱과 함께 업데이트하세요. GUI: `⇧⌘A` › Production Log… · TUI: `⌃k` › Production Log…. 설정 폴더에 저장됩니다 (`audit.jsonl`, 본인만 읽을 수 있음, 최근 2,000개).
- **되돌리기 SQL**: Production Data Source (PostgreSQL, MySQL) 에서 테이블 하나에 대한 단순한 `UPDATE` / `DELETE` 를 실행하기 직전에 바뀔 행을 떠 두고 (최대 1,000 행), 되돌리는 SQL 을 기록에 남깁니다. 행은 그 문장과 같은 트랜잭션에서 잠그며 (`SELECT … FOR UPDATE`) 읽으므로, 그 사이에 다른 세션이 바꿀 수 없습니다: Auto 모드에서는 전처럼 문장이 끝나면 바로 커밋되고, 직접 연 트랜잭션 (Manual, 또는 `BEGIN`) 에서는 둘 다 그 트랜잭션 안에서 실행됩니다. PostgreSQL 에서 `UPDATE` 는 `UPDATE` 자체가 거는 잠금 (`FOR NO KEY UPDATE`) 만 걸어서, 다른 세션이 자식 행을 넣는 것을 막지 않습니다. `UPDATE` 권한이 없는 역할 (예: `SELECT` 와 `DELETE` 만) 은 행을 잠글 수 없어서 잠그지 않고 읽습니다. 행을 기다리는 동안 취소하거나 서버가 기다리기를 그만두면 (시간 초과, 교착 상태) 그 문장은 아예 실행하지 않습니다. MySQL 에서 교착 상태는 열려 있는 트랜잭션 전체를 되돌리므로, 앞서 커밋하지 않은 변경이 사라졌다고 알려 줍니다. 저절로 실행하지 않습니다: 기록에서 콘솔로 열어 확인하고 실행하세요 (그때도 Production 확인을 거칩니다). 테이블에 PK 가 없거나, 문장이 PK 를 바꾸거나, 실행 직전에 떠 둔 행보다 많은 행을 바꾸면 (실행 중에 조건에 새로 맞게 된 행, 잠그며 읽을 때 행을 가리는 행 수준 보안, 트리거) 남기지 않습니다.
- **Explain Analyze** 는 문장을 실제로 실행합니다. PostgreSQL · MySQL 에서는 트랜잭션 안에서 실행하고 되돌립니다 — `SELECT` 가 부르는 함수도 데이터를 바꿀 수 있으므로 읽기 문장도 포함해 모든 문장을 — 그래서 테이블 변경은 되돌려집니다 (MySQL 에서는 트랜잭션 테이블 (InnoDB) 만이고, MyISAM · MEMORY 테이블의 변경은 남습니다). 다른 데이터 소스에서는 트랜잭션으로 감싸지 않고, 데이터를 바꾸는 문장이면 먼저 묻습니다 ("it changes data"). 문장이 트랜잭션 밖에서 한 일은 되돌릴 수 없습니다 — 시퀀스 값 (`nextval`, `setval`), 다른 서버의 `dblink_exec`, 파일 (`SELECT … INTO OUTFILE`), advisory 잠금, 소비된 복제 슬롯. 선택 영역을 한 문장으로 실행할 때 첫 문장 뒤의 `COMMIT` 이나 MySQL DDL 도 마찬가지입니다 (첫 문장만 Explain 되고 나머지는 그대로 실행됩니다). 이런 경우 먼저 묻고 ("a rollback can't undo …"), Qurry 가 모르는 함수를 부르는 `SELECT` 도 먼저 묻습니다 (사용자 정의 함수나 목록에 없는 내장 함수: "it calls f(), and a rollback can't undo what a function does outside the transaction"). 계속하려면 Run Anyway, 아무것도 실행하지 않으려면 Cancel 이고, 실행 없이 계획만 보려면 Explain Plan 을 쓰세요. 실행 뒤 Output 에는 무엇이 남을 수 있는지 알려 줍니다. 트리거나 함수 본문 안은 볼 수 없으므로, 데이터를 바꾸는 문장이면 테이블 변경은 되돌렸지만 트리거나 함수가 트랜잭션 밖에서 한 일은 되돌리지 못했다고 알려 줍니다. `INSERT` 가 serial · `AUTO_INCREMENT` 열에서 받은 번호도 다시 쓰이지 않지만, 이것은 묻지 않습니다. "dangerous statement" 질문 (`WHERE` 없는 `DELETE` …) 은 Explain 에서는 묻지 않습니다: 필요하면 Explain Analyze 가 자기 질문을 합니다. GUI 와 TUI 가 같은 규칙, 같은 문구로 판단합니다.
- **Auto 모드의 스크립트** 는 문장 하나씩 실행합니다. 중간에 실패하면 앞에서 이미 커밋된 문장이 몇 개인지 출력에 알려 줍니다.
- **테이블 편집기** 는 모든 편집을 트랜잭션 하나로 저장하고, `UPDATE`/`DELETE` 하나가 정확히 한 행만 바꿔야 합니다. 아니면 아무것도 저장하지 않습니다.
- **Data Source 파일 가져오기** 는 무엇이 바뀌는지 먼저 보여 줍니다 (예: "turns Read-only OFF", "turns SSL OFF", 다른 서버, 새 시작 스크립트).
- **MCP 서버** (AI 도구): Data Source 마다 MCP 를 Off · Read · Read & write 로 정합니다. 새 Data Source 는 Off 로 시작하고, Production 은 켜 주기 전까지 보이지 않습니다 ([MCP 서버](mcp.md)). 읽기 전용 검사는 두 번째 방어선입니다: MCP 에는 따로 **최소 권한 DB 사용자** (읽기 전용 역할. superuser, `FILE`, `pg_read_server_files`, `pg_signal_backend`, `dblink` 없음) 를 주세요. 검사가 모르는 함수가 있어도 해를 끼치지 못합니다.
- **저장된 비밀번호** 는 저장할 때의 서버로만 보냅니다: 종류 · 호스트 · 포트 · 사용자 · SSH 터널을 바꾸거나 SSL 을 끄면 Test 와 Save 가 비밀번호를 다시 묻고, 같은 Data Source 로 다른 서버를 가져오거나 "Allow unencrypted connection" 을 켜는 파일을 가져오면 저장된 비밀번호를 지웁니다. 드라이버와 임베딩 요청은 리다이렉트를 따라가지 않고, OpenAI 키는 OpenAI (또는 `OPENAI_BASE_URL` 의 서버) 로만 보내며 인덱스마다 적은 "OpenAI 호환" 서버로는 보내지 않습니다.
- **쿼리 히스토리** (GUI) 는 `CREATE/ALTER USER … PASSWORD '…'`, `IDENTIFIED BY '…'`, Redis `AUTH` 의 비밀번호를 가립니다.
- **릴리스** 는 `main` (beta) 과 `main` 에 있는 버전 태그 (stable, [업데이트](updates.md#릴리스가-만들어지는-방식) 참고) 에서만, 커밋 SHA 로 고정한 GitHub Actions 로 빌드하고 `SHA256SUMS` 와 빌드 출처 증명 (provenance attestation) 을 붙입니다. 업데이트 서명 키는 빌드와 분리된 서명 단계에서만 씁니다. GUI 는 업데이트 묶음의 서명을, `qurry-tui --update` 는 `SHA256SUMS` 의 서명 (같은 키) 과 체크섬을 확인한 뒤 설치합니다.
