# 안전장치

[English](../safety.md) | 한국어

- **읽기 전용 Data Source** 는 화면만이 아니라 엔진이 지킵니다: 모든 콘솔, 테이블 편집기, Redis, 내보내기에서 읽는 문장만 실행합니다 (트랜잭션 제어와 `SET` 은 되지만 읽기 전용을 끄는 것은 안 됨).
- **트랜잭션**: 직접 연 트랜잭션 (Manual 모드, 또는 Auto 모드의 `BEGIN`) 은 결과를 나눠 받는 동안 몰래 커밋되거나 되돌려지지 않습니다. 커밋 안 한 변경이 있을 때 Manual → Auto 로 바꾸면 먼저 묻고, 탭 닫기 · 연결 끊기 · 데이터베이스 바꾸기 · 종료도 되돌리기 전에 묻습니다. 열린 트랜잭션이 있는 Data Source 는 자동으로 연결이 끊기지 않습니다. Manual 모드에서는 `SHOW` / `SET` / `USE` 말고는 `SELECT` 도 트랜잭션을 엽니다 (`FOR UPDATE` 로 행을 잠그거나, 데이터를 바꾸는 함수를 부를 수 있으므로). 그래서 MySQL 에서도 PostgreSQL 처럼 그 뒤에 Commit / Roll back 이 보입니다. MySQL 에서는 실패한 문장 뒤에도 그렇습니다. 서버가 트랜잭션을 열어 둔 채로 두기 때문입니다 (그 문장이 건 행 잠금, 프로시저가 실패하기 전에 바꾼 것). MySQL 은 DDL (임시 테이블 제외), `LOCK TABLES`, `BEGIN`, 테이블 관리 문장 (`ANALYZE TABLE`, `OPTIMIZE` …), 계정 · 플러그인 문장 (`SET PASSWORD`, `INSTALL PLUGIN` …), autocommit 이 꺼져 있을 때의 `SET autocommit = 1` 앞에서 열린 트랜잭션을 스스로 커밋합니다. 임시 테이블에 대한 문장, MariaDB 의 `ANALYZE SELECT` / `ANALYZE UPDATE` …, autocommit 이 이미 켜져 있을 때의 `SET autocommit = 1`, `BEGIN` 뒤의 `UNLOCK TABLES` (`BEGIN` 이 이미 잠금을 풀었으므로) 는 커밋하지 않습니다. Qurry 는 단어로 짐작하지 않습니다. 열린 트랜잭션에서 (그리고 MySQL Manual 모드에서) `SELECT` 나 행 변경 (`INSERT`, `UPDATE`, `DELETE` …) 이 아닌 문장을 실행한 뒤에는 서버에 트랜잭션이 아직 열려 있는지 묻고 (아무것도 바꾸지 않는 방법으로 묻기 때문에, 미리 해 둔 `SET TRANSACTION ISOLATION LEVEL …` 은 다음 트랜잭션에 그대로 적용됩니다), 커밋됐으면 운영 작업 기록에 "COMMIT (implicit)" 로 남깁니다. 그런 문장이 실패한 뒤에도 똑같이 묻습니다. DDL, `LOCK TABLES`, `SET PASSWORD`, `ALTER USER`, `INSTALL PLUGIN` 은 그 뒤에 실패해도 (이미 있는 열, 없는 테이블이나 사용자, 없는 플러그인 파일) 커밋하는 경우가 많지만, 그 전에 실패하면 (문법 오류, 너무 긴 이름, 선택한 데이터베이스 없음) 커밋하지 않고, 오류 번호로는 어느 쪽인지 알 수 없습니다. 커밋됐으면 콘솔이 그렇게 알려 주고 (오류 메시지로, 문장이 실행됐으면 경고로), 앞의 변경은 Roll back 으로 더 되돌릴 수 없습니다 (Production Data Source 에서는 남길 수 있었던 변경의 되돌리는 SQL 이 운영 작업 기록에 있습니다). `CALL` (또는 준비된 문장의 `EXECUTE`, MariaDB 의 `BEGIN NOT ATOMIC … END` 블록. 이 블록은 `BEGIN` 이 아닙니다. 뒤에 주석이 붙은 `BEGIN` 은 그대로 `BEGIN` 입니다) 은 그 안에서 트랜잭션을 커밋하거나 되돌릴 수 있고, 메타데이터 잠금을 기다리다 시간 초과나 교착 (1205 / 1213) 으로 실패한 DDL 은 이미 커밋한 뒤이며, `SET` 안의 교착은 트랜잭션을 되돌립니다. 이런 문장에서 트랜잭션이 끝났으면 서버의 답으로는 어느 쪽인지 알 수 없으므로, 콘솔이 그렇게 알리고 데이터를 확인하라고 하며, 운영 작업 기록에는 "ENDED (committed or rolled back)" 로 남기고 결과를 알 수 없음 (outcome unknown) 으로 보여 줍니다. 트랜잭션 밖의 Auto 모드에서도 `CALL`, `EXECUTE`, `BEGIN NOT ATOMIC` 블록 뒤에는 묻습니다. 트랜잭션을 시작하고 커밋하지 않는 프로시저는 트랜잭션을 열어 둔 채 끝나기 때문이며, 그러면 콘솔이 트랜잭션을 열린 것으로 보여 주고 Commit / Roll back 을 띄웁니다. 서버가 답하지 못하면 (MySQL 5.6, 또는 TiDB 처럼 트랜잭션 안에서도 그 질문을 받아들이는 MySQL 호환 서버. 콘솔이 연결할 때 Qurry 가 확인합니다) 트랜잭션이 열려 있는 것으로 둡니다. 그런 서버에서 DDL 뒤에는 Commit 을 눌러 닫으세요 (더 저장되는 것은 없습니다). MySQL 5.7 이상에서는 묻는 동안 그 문장의 경고가 지워집니다. 열린 트랜잭션에서 그런 문장 바로 뒤에 `SHOW WARNINGS` 를 실행하면 그 문장의 경고가 아니라 오류 1766 (session_track_gtids) 이 나옵니다. 경고를 봐야 하면 (예: `ALTER TABLE` 이 데이터를 잘랐는지) 트랜잭션 밖의 Auto 모드에서 실행하세요. 그때는 Qurry 가 묻지 않습니다 (`CALL`, `EXECUTE` 뒤에는 묻기 때문에 그 경고는 콘솔에서 볼 수 없습니다).
- **Production 트랜잭션** (#106): Production Data Source 의 새 콘솔은 Tx: Manual 로 시작하므로, 바꾼 내용은 Commit 이나 Roll back 을 할 때까지 커밋되지 않고 남아 있습니다 (Data Source Properties › Options › **Production: start consoles in Manual transaction mode**, 기본으로 켜짐. TUI: Data Source 폼의 `Production Manual`. 끄면 콘솔은 Transaction control 모드로 시작합니다). Data Source 마다 처음 그렇게 열린 콘솔이 한 번 Output 에 알리고 (TUI: 상태줄에도), 어디서 끄는지 알려 줍니다. 트랜잭션이 열린 콘솔은 Commit / Roll back 옆에 **● Transaction pending** 을 보여 주고, Production 에서는 빨간색입니다 (TUI: 제목에 "pending" 과 Commit · Roll back 키). Auto 모드에서 직접 친 `BEGIN` 에도 Commit / Roll back 이 나옵니다. 탭을 닫거나, 데이터베이스를 바꾸거나, 연결을 끊거나, 종료할 때는 열린 트랜잭션이 있으면 늘 그렇듯 먼저 묻습니다. Production 트랜잭션에서 5분 동안 문장을 실행하지 않으면 한 번 알립니다 (Output, 배지의 툴팁, 상태줄): 변경이 아직 저장되지 않았고 바꾼 행이 잠겨 있다는 것, 그리고 서버에 한도가 있으면 그 한도. 문장을 실행하거나 Commit / Roll back 하면 기다림이 다시 시작됩니다. 서버가 트랜잭션 안에서 놀고 있던 세션을 끝내면 (PostgreSQL `idle_in_transaction_session_timeout`, MySQL `wait_timeout`), 다음 문장이나 Commit 이 그 설정 이름과 함께 트랜잭션이 되돌려졌고 더 보낸 것이 없다고 알리며, 운영 작업 기록에는 "ROLLBACK (by the server)" 가 남습니다 (이때의 Commit 은 결과를 모르는 것이 아닙니다: 서버가 받지 못했습니다). Keep-alive 쿼리 (Options) 는 PostgreSQL 의 한도에서 문장으로 칩니다. MCP 의 쓰기 (`--allow-write` 로 켠 `execute`) 는 콘솔을 쓰지 않아서, 예전처럼 각각 자기 트랜잭션에서 실행되고 커밋됩니다.
- **다시 연결된 뒤 더 불러오기**: Data Source 설정을 저장하거나, 연결을 끊거나, 쓰지 않아 자동으로 끊기면 그 콘솔들의 연결이 닫힙니다. 열려 있던 결과 (콘솔, 테이블 탭) 를 계속 스크롤하면 그 문장을 새 연결에서, 실행했던 스키마 (PostgreSQL `search_path`, MySQL `USE`) 에서, 이미 보인 행 다음부터 다시 엽니다 (1분 동안 쓰지 않아 닫힌 결과를 다시 열 때와 같습니다). `ORDER BY` 가 없으면 순서는 서버가 정하고, 그 사이 바뀐 행은 빠지거나 두 번 보일 수 있습니다. Data Source 가 이제 다른 서버나 데이터베이스를 가리키면 (호스트, 포트, 사용자, 종류, 터널, 데이터베이스가 바뀌었거나 SSL 을 낮춘 경우) 또는 연결 직후 실행하는 설정이 바뀌었으면 (시작 스크립트, 시간대, 격리 수준), 결과를 트랜잭션 (Manual 모드나 `BEGIN`) 안에서 읽었다면 (그 트랜잭션은 이전 연결과 함께 끝났습니다), 실행했던 스키마를 읽지 못했다면, 또 문장이 그냥 읽기가 아니면 (`nextval`, `pg_sleep`, `pg_notify`, `get_lock` 처럼 부수 효과가 있는 함수를 부르거나, `FOR UPDATE`, `FOR SHARE`, `FOR KEY SHARE`, `LOCK IN SHARE MODE` 로 행을 잠그는 등) 다시 열지 않습니다: 그리드에 "Couldn't load more rows: …" 와 이유가 남고 (GUI: 툴바의 행 수 옆, **Run again** 버튼과 함께 · TUI: 그리드 아래 테두리) 상태 표시줄에도 나오며, 행 수의 `+` 도 그대로이고, 쿼리를 다시 실행하면 처음부터 불러옵니다. 탭을 다시 실행한 뒤에 도착한 행은 버리고, 탭이 다시 실행되는 동안 요청한 더 불러오기는 새 결과의 행을 가져가지 않습니다. 읽기 전용 Data Source 는 다시 열기 전에 문장을 다시 검사합니다.
- **확인**: `WHERE` 없는 `UPDATE`/`DELETE`, `DROP`, `TRUNCATE`, Redis `FLUSHALL`/`FLUSHDB`/`DEL` 은 실행 전에 묻습니다 (GUI, TUI, Redis Terminal 도. Production 에서는 Redis Terminal 의 모든 쓰기 전에 묻습니다).
- **Production Data Source** 는 바꾸는 문장이 몇 행을 건드리는지 보여 주고 실행 전에 묻습니다 ([Data Source](data-sources.md)). 이 질문은 행을 다 센 뒤에 뜨므로, TUI 에서는 그동안 계속 친 키로 답해지지 않습니다: `y` / `Enter` 는 잠시 멈춘 뒤에만 답합니다 (키를 누를 때마다 기다림이 다시 시작되고, `n` / `Esc` 는 바로 취소). 다른 대화 상자에 입력하는 중이면 그 창을 닫을 때까지 기다립니다. 저절로 뜨는 다른 질문 (드라이버 다운로드, 마이그레이션, 테스트 데이터, 관련 행 복사) 과 알림에 가려져 있던 질문도 같습니다. 그동안 다른 탭으로 옮겼더라도 yes 는 물어본 그 콘솔을 다시 보여 주고 거기서 실행합니다. 그 콘솔을 닫았다면 아무것도 실행하지 않습니다.
- **Production 에서 그리드 수정** (테이블 탭, 또는 콘솔 결과): Submit 은 실행할 문장을 보여 주고 저장 전에 묻습니다 (`UPDATE` / `DELETE` 하나가 정확히 한 행을 바꾸지 않으면 아무것도 저장하지 않습니다). Auto 모드의 그리드 수정은 콘솔 세션이 아닌 별도 연결에서 저장되므로, 콘솔에서 한 `SET ROLE`, 세션 설정, 임시 테이블은 적용되지 않습니다. 그래서 임시 테이블이나 행을 잠그는 읽기 (`FOR UPDATE`, `LOCK IN SHARE MODE` …) 의 결과는 읽기 전용입니다. Manual 모드이거나 트랜잭션이 열려 있으면 Submit 은 그 콘솔의 트랜잭션 안에서 savepoint 를 두고 실행합니다 (질문에 그렇게 나옵니다): 하나가 실패하거나 정확히 한 행을 바꾸지 않으면 그 Submit 만 되돌리고 트랜잭션은 계속됩니다. 수정은 Commit / Roll back 할 때까지 커밋되지 않고, 운영 작업 기록에는 커밋 전으로, 되돌리기 SQL 과 함께 남습니다.
- **조인 결과 수정** (#102): 조인의 컬럼은 그 컬럼의 테이블이 기본 테이블 (뷰, 구체화 뷰, 외부 테이블, 임시 테이블이 아님) 이고 그 테이블의 기본 키 전체가 결과에 있으면 그 테이블에서 수정됩니다. 수정한 행과 테이블마다 `UPDATE <table> SET … WHERE <key> = …` 하나가 되고 (키 값은 읽었을 때의 값), 같은 Submit 을 거칩니다 (각각 정확히 한 행, 읽기 전용 Data Source 는 거부, Production 질문과 기록). 나머지 컬럼은 읽기 전용이고 이유를 알려 줍니다: GUI 는 헤더를 흐리게 하고 🔒 를 붙이며 마우스를 올리면 이유를 보여 주고 (그 행에만 해당하는 이유는 셀에), TUI 는 수정 키를 누르면 상태줄에 알려 줍니다 ("Read-only: the result doesn't include the primary key of public.users (idx).", "… is computed …"). 외부 조인에서 어떤 테이블의 행이 맞지 않은 줄 (그 줄에서 키가 NULL) 의 셀은 읽기 전용입니다. 자기 자신과 조인한 테이블은 나온 자리마다 그 자리의 키 컬럼으로 따로 수정하므로, 두 자리의 키를 모두 `alias.column` 으로 고르세요. 컬럼이 어느 자리인지 Qurry 가 알 수 없으면 그 이유와 함께 읽기 전용입니다. 두 테이블에 같은 이름의 컬럼 (`idx`, `status`) 이 있어도 각자 자기 테이블로 갑니다: PostgreSQL 은 결과 컬럼마다 어느 테이블의 몇 번째 컬럼인지 알려 주고, 드라이버로 그것을 알려 주지 않는 MySQL 은 select 목록을 각 테이블의 컬럼과 서버가 돌려준 이름에 맞춰 봅니다 (`USING` 이나 `NATURAL` 이 있는 조인의 맨 `*` 는 합쳐진 컬럼이 한 번만 나와서 읽기 전용입니다. `alias.*` 를 쓰세요). 조인 결과에서는 행을 추가 · 복제 · 삭제할 수 없습니다. 한 행이 한 테이블의 행이 아니기 때문입니다.
- **운영 작업 기록**: Production Data Source 에서 실행한 바꾸는 문장 (콘솔, 테이블 편집기, 테스트 데이터, 복사) 을 시각 · Data Source · 바뀐 행 수 · 커밋 전이었는지와 함께 남기고, 뒤의 COMMIT / ROLLBACK 도 남깁니다. 바꾸는 문장은 실행하기 전에 먼저 기록하므로, 실행 중에 Qurry 가 멈춰도 기록에 남습니다. 기록을 쓸 수 없으면 (디스크가 가득 참, 파일이나 설정 폴더에 쓰기 권한이 없음) 그 문장과, 기록된 변경의 COMMIT 은 실행하지 않고 무엇을 고치면 되는지 알려 줍니다. 고친 뒤 다시 실행하세요 (ROLLBACK 은 언제나 실행됩니다). 실행은 됐는데 결과를 기록하지 못하면 오류가 아니라 경고로 알려 줍니다: 이미 실행됐으니 다시 실행하지 마세요. 기록에는 "no result recorded" 로 보이며, 아직 실행 중이거나 Qurry 가 멈춰 끊긴 변경도 그렇게 보입니다. 기록된 변경이 있는 트랜잭션을 서버가 COMMIT 없이 끝내면 (교착 상태, 실패한 COMMIT, 끊긴 연결) "ROLLBACK (by the server)" 로 남깁니다. PostgreSQL 에서는 문장 하나가 실패하면 트랜잭션이 중단되고, 그 뒤의 COMMIT 은 되돌리기만 합니다. Qurry 는 "Not committed" 로 알려 주고, 기록에는 실패한 COMMIT 다음에 "ROLLBACK (by the server)" 를 남깁니다 (실패한 문장을 빼고 변경을 다시 실행하세요. COMMIT 전에 `ROLLBACK TO SAVEPOINT` 를 하면 나머지는 남습니다). 그런 트랜잭션이 열린 채로 연결을 끊으면 (또는 Data Source 설정을 바꾸면) "ROLLBACK (disconnected)" 로 남깁니다. COMMIT 도중에 연결이 끊기면 서버가 끊기기 전에 커밋했을 수도 있으므로 "COMMIT outcome unknown (connection lost)" 로 남기고, Commit 버튼의 알림 제목도 "Commit failed" 가 아니라 "Commit outcome unknown" 입니다. 변경을 다시 실행하기 전에 데이터를 먼저 확인하세요. 이전 버전의 Qurry 는 Production 변경을 하나마다 두 번 (실행 전, 결과) 보여 주므로, TUI (Homebrew 등) 도 앱과 함께 업데이트하세요. GUI: `⇧⌘A` › Production Log… · TUI: `⌃k` › Production Log…. 설정 폴더에 저장됩니다 (`audit.jsonl`, 본인만 읽을 수 있음, 최근 2,000개).
- **되돌리기 SQL**: Production Data Source (PostgreSQL, MySQL) 에서 테이블 하나에 대한 단순한 `UPDATE` / `DELETE` 를 실행하기 직전에 바뀔 행을 떠 두고 (최대 1,000 행), 되돌리는 SQL 을 기록에 남깁니다. 행은 그 문장과 같은 트랜잭션에서 잠그며 (`SELECT … FOR UPDATE`) 읽으므로, 그 사이에 다른 세션이 바꿀 수 없습니다: Auto 모드에서는 전처럼 문장이 끝나면 바로 커밋되고, 직접 연 트랜잭션 (Manual, 또는 `BEGIN`) 에서는 둘 다 그 트랜잭션 안에서 실행됩니다. PostgreSQL 에서 `UPDATE` 는 `UPDATE` 자체가 거는 잠금 (`FOR NO KEY UPDATE`) 만 걸어서, 다른 세션이 자식 행을 넣는 것을 막지 않습니다. `UPDATE` 권한이 없는 역할 (예: `SELECT` 와 `DELETE` 만) 은 행을 잠글 수 없어서 잠그지 않고 읽습니다. 행을 기다리는 동안 취소하거나 서버가 기다리기를 그만두면 (시간 초과, 교착 상태) 그 문장은 아예 실행하지 않습니다. MySQL 에서 교착 상태는 열려 있는 트랜잭션 전체를 되돌리므로, 앞서 커밋하지 않은 변경이 사라졌다고 알려 줍니다. 저절로 실행하지 않습니다: 기록에서 콘솔로 열어 확인하고 실행하세요 (그때도 Production 확인을 거칩니다). 테이블에 PK 가 없거나, 문장이 PK 를 바꾸거나, 실행 직전에 떠 둔 행보다 많은 행을 바꾸면 (실행 중에 조건에 새로 맞게 된 행, 잠그며 읽을 때 행을 가리는 행 수준 보안, 트리거) 남기지 않습니다.
- **Explain Analyze** 는 문장을 실제로 실행합니다. PostgreSQL · MySQL 에서는 트랜잭션 안에서 실행하고 되돌립니다 — `SELECT` 가 부르는 함수도 데이터를 바꿀 수 있으므로 읽기 문장도 포함해 모든 문장을 — 그래서 테이블 변경은 되돌려집니다 (MySQL 에서는 트랜잭션 테이블 (InnoDB) 만이고, MyISAM · MEMORY 테이블의 변경은 남습니다). 다른 데이터 소스에서는 트랜잭션으로 감싸지 않고, 데이터를 바꾸는 문장이면 먼저 묻습니다 ("it changes data"). 문장이 트랜잭션 밖에서 한 일은 되돌릴 수 없습니다 — 시퀀스 값 (`nextval`, `setval`), 다른 서버의 `dblink_exec`, 파일 (`SELECT … INTO OUTFILE`), advisory 잠금, 소비된 복제 슬롯. 선택 영역을 한 문장으로 실행할 때 첫 문장 뒤의 `COMMIT` 이나 MySQL DDL 도 마찬가지입니다 (첫 문장만 Explain 되고 나머지는 그대로 실행됩니다). 이런 경우 먼저 묻습니다 ("a rollback can't undo …"). `WHERE` 없는 `UPDATE` · `DELETE` 도 먼저 묻습니다 (모든 행을 바꾸고 되돌릴 때까지 잠그므로 그 테이블에 쓰는 다른 세션이 기다립니다. MyISAM · MEMORY 테이블의 변경은 남습니다). 계속하려면 Run Anyway, 아무것도 실행하지 않으려면 Cancel 이고, 실행 없이 계획만 보려면 Explain Plan 을 쓰세요. 실행 뒤 Output 에는 무엇이 남을 수 있는지 알려 줍니다. 트리거나 함수 본문 안은 볼 수 없으므로, 데이터를 바꾸는 문장이면 테이블 변경은 되돌렸지만 트리거나 함수가 트랜잭션 밖에서 한 일은 되돌리지 못했다고 알려 주고, 사용자 정의 함수를 부르는 문장이라고 따로 묻지는 않습니다: 그 함수의 테이블 변경도 되돌려지지만, 트랜잭션 밖에서 한 일 (시퀀스 값, `dblink`) 은 남습니다. 잘 모르는 함수라면 Explain Plan 을 쓰세요. `INSERT` 가 serial · `AUTO_INCREMENT` 열에서 받은 번호도 다시 쓰이지 않지만, 이것은 묻지 않습니다. Explain 은 "dangerous statement" 질문을 따로 하지 않고 한 번만 묻습니다: `WHERE` 없는 `DELETE` 이면 Explain Analyze 의 질문이 그 이유를 말하고, Production 데이터 소스에서는 행 수 확인 대신 이 질문을 합니다. 트랜잭션이 열려 있으면 (Manual 모드, 직접 실행한 `BEGIN`, `COMMIT AND CHAIN` · `ROLLBACK AND CHAIN` 이 바로 여는 다음 트랜잭션, MySQL 에서 Qurry 가 열린 것을 못 본 트랜잭션 (`/*! … */` 주석 안의 `START TRANSACTION` 등), 어떤 방법으로든 autocommit 을 끈 경우: `SET autocommit = 0`, 프로시저, 덤프의 `/*!40101 … */` 머리말) `SAVEPOINT` … `ROLLBACK TO SAVEPOINT` 로 감싸므로, 커밋하지 않고 둔 작업은 커밋되지 않은 채 남고 (MySQL 에서 `BEGIN` 을 보내면 커밋됩니다) Commit · Roll back 은 직접 고르면 됩니다. 읽기 전용 데이터 소스에서도 마찬가지입니다. GUI 와 TUI 가 같은 규칙, 같은 문구로 판단합니다.
- **Auto 모드의 스크립트** 는 문장 하나씩 실행합니다. 중간에 실패하면 앞에서 이미 커밋된 문장이 몇 개인지 출력에 알려 줍니다.
- **테이블 편집기** 는 모든 편집을 트랜잭션 하나로 저장하고, `UPDATE`/`DELETE` 하나가 정확히 한 행만 바꿔야 합니다. 아니면 아무것도 저장하지 않습니다.
- **Data Source 파일 가져오기** 는 무엇이 바뀌는지 먼저 보여 줍니다 (예: "turns Read-only OFF", "turns SSL OFF", 다른 서버, 새 시작 스크립트).
- **MCP 서버** (AI 도구): Data Source 마다 MCP 를 Off · Read · Read & write 로 정합니다. 새 Data Source 는 Off 로 시작하고, Production 은 켜 주기 전까지 보이지 않습니다 ([MCP 서버](mcp.md)). 읽기 전용 검사는 두 번째 방어선입니다: MCP 에는 따로 **최소 권한 DB 사용자** (읽기 전용 역할. superuser, `FILE`, `pg_read_server_files`, `pg_signal_backend`, `dblink` 없음) 를 주세요. 검사가 모르는 함수가 있어도 해를 끼치지 못합니다.
- **저장된 비밀번호** 는 저장할 때의 서버로만 보냅니다: 종류 · 호스트 · 포트 · 사용자 · SSH 터널을 바꾸거나 SSL 을 끄면 Test 와 Save 가 비밀번호를 다시 묻고, 같은 Data Source 로 다른 서버를 가져오거나 "Allow unencrypted connection" 을 켜는 파일을 가져오면 저장된 비밀번호를 지웁니다. 드라이버와 임베딩 요청은 리다이렉트를 따라가지 않고, OpenAI 키는 OpenAI (또는 `OPENAI_BASE_URL` 의 서버) 로만 보내며 인덱스마다 적은 "OpenAI 호환" 서버로는 보내지 않습니다.
- **암호화 없는 연결** 은 Production 에서 클릭 한 번으로 켜지지 않습니다: TLS 가 없는 서버에 연결이 실패하면 개발 · LAN Data Source 는 **Allow unencrypted for this data source** 버튼을 보여 주지만 (그 호스트로 비밀번호가 암호화 없이 간다고 알려 줌), Production 은 보여 주지 않습니다. 그곳에서 암호화를 끄는 것은 설정이 보이는 Data Source 폼에서 직접 고르는 일이고, 엔진도 Production 에는 이 길을 거부합니다. 이 확인은 실수로 누른 키로 답해지지 않습니다: TUI 에서는 잠시 멈춘 뒤 누른 `y` 로만 답합니다 (Enter 와 계속 타이핑하던 키는 무시: 키를 누를 때마다 기다림이 다시 시작됩니다. `n` / `Esc` 는 바로 취소). 콘솔은 그 뒤 문장을 다시 실행하지 않고 다시 연결만 합니다 ([Data Source](data-sources.md)).
- **쿼리 히스토리** (GUI, TUI, Redis Terminal 의 ↑↓ 도) 는 `CREATE/ALTER USER … PASSWORD '…'`, `IDENTIFIED BY '…'`, Redis `AUTH`, `HELLO … AUTH`, `CONFIG SET requirepass` / `masterauth`, `ACL SETUSER` 의 `>비밀번호` / `#해시` 규칙, `MIGRATE … AUTH` / `AUTH2` 의 비밀번호를 가립니다 (인자 단위로 가려서, 따옴표로 감싼 공백 든 비밀번호도 통째로 가립니다).
- **릴리스** 는 `main` (beta) 과 `main` 에 있는 버전 태그 (stable, [업데이트](updates.md#릴리스가-만들어지는-방식) 참고) 에서만, 커밋 SHA 로 고정한 GitHub Actions 로 빌드하고 `SHA256SUMS` 와 빌드 출처 증명 (provenance attestation) 을 붙입니다. 업데이트 서명 키는 빌드와 분리된 서명 단계에서만 씁니다. GUI 는 업데이트 묶음의 서명을, `qurry-tui --update` 는 `SHA256SUMS` 의 서명 (같은 키) 과 체크섬을 확인한 뒤 설치합니다.
