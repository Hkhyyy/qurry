# Data sources

English | [한국어](ko/data-sources.md)

The databases Qurry works with, how to connect to them (SSH, AWS SSM, SSL, options) and how drivers for the less common ones are added.

## Supported databases

| Database | Features |
|---|---|
| PostgreSQL | Explorer tree (databases, schemas, tables, views, sequences, routines), query console (server-side cursor paging, cancel, manual transactions), data editing, explain plan, DDL, full-text search. `infinity` / `-infinity` dates and timestamps show as such, and arrays of them show their values |
| MySQL / MariaDB | Same as above. A MySQL database is its own schema, so tables appear directly under the database |
| Redis | Medis-style browser (key list with type and TTL, per-type value editor), redis-cli style terminal with completion, **Standalone / Sentinel / Cluster** ([Redis browser](#redis-browser)) |

Connection options:
- **SSH tunnel** with a key or password. Host keys are checked against `~/.ssh/known_hosts`: a changed key is refused, and an unknown server stops with its SHA256 fingerprint until you choose **Trust host key** (GUI: data source dialog; TUI: `⌃y` in the form or `⌃k › Trust SSH Host Key`). The tunnel listens on a random port on `127.0.0.1` while the data source is connected; other programs on the same computer could use that port too, so on a shared machine use database passwords (not only the bastion's IP allow-list) and set **Auto-disconnect** so idle tunnels close. One SSH session serves all databases of the data source; when it ends (the laptop sleeps, the network changes), the next query logs in again. When the session stays open but nothing comes through it any more, a connect that gets no answer within 10 seconds first checks the tunnel with a new connection that must get the database's first bytes within 2 seconds (5 seconds while a console of the data source has a transaction open or a statement running, or an export, import, backup, restore or subset copy runs on it; Auto-disconnect waits for those too). When that gets nothing either, Qurry logs in again and tries once more, and that query goes on (a console's transaction through the dead session is lost: nothing reaches it any more). A console or table tab whose session is already open checks it first when it sat unused for 10 seconds (by the clock, so time the computer slept counts): when it gets no answer within 5 seconds, Qurry closes it (and the tunnel, when that carries nothing either) and runs the statement once in a new session. When a transaction was open in it and the tunnel still answers, the session is only slow (the network coming back after sleep, a tunnel busy with a backup): Qurry keeps it with the transaction, sends nothing and says so; run it again or Roll back. When the tunnel carries nothing either, the transaction is lost: the run (or Commit) says so and sends nothing, so run it again. Every other console whose transaction was closed with the tunnel, or by Disconnect, says so too on its next run, Commit or Roll back, once, instead of running it in a new session. A statement already waiting through the dead session ends with "The connection through the SSH tunnel (…) closed" when you press Cancel, or at the next keep-alive when Keep-alive is turned on (Options); it is never run again by itself. The status line then says why the data source was disconnected ("Disconnected: the SSH tunnel of <name> stopped answering — the next query opens a new one"). When the tunnel still answers, it is kept with everything that runs through it (consoles, imports, restores), and the error says the tunnel answers and what else can hold a connect up: all 32 connections of the data source in use (open consoles and tables), a slow database, or a startup script that fails or runs long. This covers PostgreSQL and MySQL data sources, and Redis consoles without SSL (they check the same way when they sat unused); for other Redis uses and plugin-driver databases (SQL Server, MongoDB, ClickHouse, Oracle …), disconnect the data source and connect again; when the database doesn't answer through the new session either, the error says so once, naming the SSH server ("Can't connect to … through the SSH tunnel (bastion:22)"): check that the database is up and that the SSH server can reach it, then run it again.
  - **ssh-agent and `~/.ssh/config`**, as `ssh` uses them. Leave the private key empty (or choose Password and leave it empty) and Qurry logs in with ssh-agent (`SSH_AUTH_SOCK`), then the `IdentityFile` keys of `~/.ssh/config` (or `~/.ssh/id_ed25519`, `id_ecdsa`, `id_rsa`); a key with a passphrase is used through the agent (`ssh-add`). The agent's keys that match an `IdentityFile` (its `.pub`) are offered first, so a server's limit on tries (`MaxAuthTries`, 6 by default) isn't used up by other keys; with `IdentitiesOnly yes` only those are offered. A key file or password you enter is used as before. The SSH host may be a `Host` alias of `~/.ssh/config`: its `HostName`, `User` (when the data source's user is empty), `Port` (when the data source's port is the default 22), `IdentityFile`, `IdentityAgent`, `IdentitiesOnly` and `ProxyJump` apply, with `Host` patterns (`*`, `?`, `!`), first value wins and `Include`, the way OpenSSH reads them. **ProxyJump** chains (`ProxyJump a,b`, and a jump host's own `ProxyJump`) go through each host in turn; jump hosts log in with the agent or their `IdentityFile` keys only, and the data source's password or key goes only to its own SSH host. Every host on the way is checked against `known_hosts`; **Trust host key** trusts the one whose fingerprint was shown, also when it is a jump host. Qurry never runs a program from `~/.ssh/config`: `ProxyCommand` is refused with its file, line and `Host` block and what to do (use `ProxyJump`, or put `ProxyCommand none` in a narrower `Host` block above it). A `ProxyCommand` under `Host *` (a Teleport, cloudflared or company proxy helper) stops every SSH tunnel whose host it matches, those with their own key or password too, so put `Host db-bastion` / `ProxyCommand none` above it for the hosts Qurry reaches directly; except the common `ssh -W %h:%p jump-host`, which is the same as `ProxyJump jump-host`. `Match` blocks are skipped. Values are checked first: a host name or user with spaces or a leading `-`, or a port that isn't a number stops the connect with the file and line. An `IdentityFile` or `IdentityAgent` with a `%` token other than `%h %p %r %u %d %%` is skipped (the login error says which line), so it doesn't stop data sources with their own key or password. This applies to saved data sources too (GUI, TUI, MCP), so a data source whose SSH host has a `Host` block in `~/.ssh/config` now uses its settings, as `ssh` would.
- **PostgreSQL passwords from `~/.pgpass`**: a data source without a saved password uses the matching line of `~/.pgpass` (or `PGPASSFILE`) for its own host, port, database and user, as `psql` does. `PGPASSWORD` isn't sent to it: an environment password is for one server, so only a [`qurry-tui` URL](tui.md#connect-from-a-url) takes it; when the login fails while `PGPASSWORD` is set, the error says to save the password or add a `~/.pgpass` line. `~/.pgpass` is read only when no one else can read it (`chmod 600 ~/.pgpass`); when it was skipped and the server refuses the login, the error says why. `PGSSLMODE` no longer changes a data source's TLS setting (the data source's SSL settings decide).
- **AWS SSM tunnel** (Session Manager port forwarding), the other choice next to SSH: GUI **SSH/SSL** tab › **Tunnel** › *AWS SSM*; TUI `Tunnel` › `aws ssm`. Enter the **AWS profile** and **region** (empty = the AWS CLI's defaults) and the **instance id** (`i-…`, or `mi-…` for a managed node); the data source's Host / Port (GUI: General tab) are the database as seen from that instance, not a port on your computer: for an RDS database behind a bastion, Host `mydb.cluster-abc.ap-northeast-2.rds.amazonaws.com` and Port `5432`. `localhost` / `127.0.0.1` is the instance itself (`::1` isn't accepted: use `127.0.0.1`); the form says so in a hint, and that is right only when the database runs on the instance. When the instance can't reach Host:Port, connecting fails with "AWS SSM: the instance couldn't reach …". Qurry runs `aws ssm start-session --document-name AWS-StartPortForwardingSessionToRemoteHost` on a random `127.0.0.1` port, waits until the plugin says it opened that port (up to 30 seconds), and connects through it. One session serves all databases of the data source. Qurry closes its sessions: when the data source disconnects, when a session doesn't open in time, and when the app quits, crashes or is stopped, it ends the session on the AWS side (`aws ssm terminate-session` with the same profile and region, on quit all at once: Qurry waits up to 2 seconds and lets slower ones finish on their own) and stops the CLI and its plugin. Stopping the CLI alone would leave the session open on the instance, and an instance with many open sessions stops opening new ones: the error then says the session started but its data channel didn't open (such sessions time out on their own). Ending sessions needs `ssm:TerminateSession` on your own sessions (without it, the CLI and plugin are still stopped); when the session ends by itself (Session Manager's idle timeout, a network drop), the next query opens a new one. When the session has died while the CLI keeps running (the laptop slept, the network changed, the session ended on the AWS side), a connect that gets no answer within 10 seconds ends it, opens a new one and tries once more, and that query goes on, also in the MCP server without a restart. As with SSH, this happens only when a 2-second check finds that the tunnel carries nothing (otherwise the tunnel is kept and the error says what else holds the connect up), and only for PostgreSQL and MySQL data sources (and Redis consoles, as for SSH); open consoles and table tabs, Cancel and the keep-alive behave as described for SSH; when the database doesn't answer through the new session either, the error says so once, naming the instance ("Can't connect to … through the AWS SSM tunnel (instance i-…)"): check that the database is up and that the instance can reach it (its security group), then run it again. Without an instance id, connecting fails and asks for it (it never connects to the host directly). Qurry stores no AWS secrets: the AWS CLI signs in with your own `~/.aws/config`, SSO login or environment. You need [AWS CLI v2](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html) and the Session Manager plugin (macOS: `brew install --cask session-manager-plugin`); the error says which one is missing. When your SSO session has expired, the error says what to run, for example `aws sso login --profile prod`. Your AWS identity needs `ssm:StartSession` on the instance and on the `AWS-StartPortForwardingSessionToRemoteHost` document, and the instance's SSM agent must be online. Several connections at once need plugin 1.2.x or later. The same note about other programs on this computer as for SSH applies to the local port. In the GUI, **Test Connection** on that tab starts a session and connects to the database (TUI: ⌃t); while it runs it shows the elapsed time, and **Cancel Test** (or Esc; TUI: ⌃t or Esc) stops it and the session. Choosing another Tunnel stops it too. A long error, such as a missing plugin with its install link, scrolls into view so you can read what to do. If the data source is disconnected or saved while a database is still connecting, that database says "The data source was disconnected while connecting. Run it again." and never keeps a connection to the closed session's port; run it again to open a new session. When several tabs or the tree open the data source at the same time and the session can't be started, they all show that one error instead of trying again one after another. A database that is missing or refused fails only where it was opened: the session stays open for the others. **Update every Qurry app on this computer first** (the GUI, and the TUI and MCP server with `brew upgrade qurry` or ⌃k › Update Qurry & Restart): older versions don't know AWS SSM and would connect to the host directly. So they never get the saved password of an SSM data source (their connection fails without it), and when they save the data sources, the SSM settings are kept for the updated apps.
- **SSL/TLS**: Require / Verify CA / Full Verification, with optional CA and client certificate. Works for PostgreSQL, MySQL and Redis. Turning SSL on starts at **Require** (shown as "encrypt, no certificate check"), which only encrypts and doesn't check the certificate, so it doesn't protect against someone in the middle posing as the server. **Full Verification** (certificate and host name) does — for a server with a private CA, together with its CA file (see below); Verify CA checks the certificate but not the host name. For PostgreSQL and MySQL, verification uses a built-in list of public CAs (not the system's trust store), so a server with a certificate from AWS RDS, a company CA or a self-signed one needs its CA file; Redis uses the system's trust store. With SSL off, a remote PostgreSQL or MySQL server must still set up TLS (the certificate isn't checked) or Qurry doesn't send the password — the same goes for backup and restore. For a server without TLS (or an old MySQL 5.7 without TLS 1.2) on a network you trust, tick **Allow unencrypted connection** in Options (TUI: `Allow unencrypted` in the data source form); Test Connection and the status bar then say "Not encrypted". When a connection fails for this reason, the error offers it in one click: **Allow unencrypted for this data source** under the explorer, console or table tab error (TUI: a confirm popup that names the data source and only `y` answers — not Enter, and only after a pause: it can appear while you are still typing, and each key typed into it starts the wait again; if another popup was open, the status line says so instead, and expanding the data source again (`←` `→`) or running again asks). It turns the setting on for that data source only and keeps its saved password; the tree then loads again and a table tab reloads, while a console only reconnects ("Connected. Run again.") and never runs the statement again; a tree still showing the error loads again too. In Data Source Properties, a failed Test Connection offers the same button, which ticks the checkbox in the form and tests again (it is saved with OK; TUI: a failed `⌃t` selects the form's `Allow unencrypted` field, `Space` turns it on and `⌃t` tests again, saved with Enter). It is never offered for **Production** data sources: the message says where the setting is, and you turn it on yourself in the form. To undo, turn off **Options ▸ Allow unencrypted connection** (TUI: `Allow unencrypted` in the data source form, `e` in the explorer). Servers on this computer (including a PostgreSQL Unix socket: a host such as `/var/run/postgresql`) and connections through an SSH or AWS SSM tunnel never need TLS. Backup and restore with MariaDB's `mysql` / `mysqldump` use its `--ssl` options; when both are installed, the MySQL client is used.
- **Options tab**: read-only, transaction control and isolation level, time zone, keep-alive, auto-disconnect when idle, single database mode, startup script.
  - **Time zone** (PostgreSQL, MySQL) is the session's time zone: a name such as `Asia/Seoul` or an offset such as `+09:00` (hours east of UTC, for PostgreSQL too). Empty is UTC: Qurry starts each session in UTC, not in the server's own setting. Values are shown in the session's zone, as `psql` and the `mysql` client show them: PostgreSQL `timestamptz` with the offset it had at that moment (`2026-11-09 13:00:00 +09:00`; across a daylight saving change each value gets its own, from this computer's time zone database), MySQL `TIMESTAMP` in the session's `time_zone` (`DATETIME` and `timestamp` without a zone are shown as stored). A `SET TIME ZONE` (MySQL `SET time_zone = …`) run in a console applies to that console's later results; there PostgreSQL reads `SET TIME ZONE '+09:00'` its own (POSIX) way, as 9 hours *west* of UTC, so use a name or `SET TIME ZONE INTERVAL '+09:00' HOUR TO MINUTE`. The grid, copy, export, CSV and MCP show the same text. Driver plugins show what the database sends: SQL Server `datetimeoffset` and Oracle `TIMESTAMP WITH TIME ZONE` with the offset stored in the value, ClickHouse `DateTime('zone')` in its zone.
- **Schemas tab**: check the databases and schemas the Database Explorer shows (nothing checked = all; expand a database for its schemas). A new data source lists them right away with the dialog's settings once they're filled in (until then the tab names what's left — host, user, file, SSH host / user, SSM instance — and doesn't connect), connecting as Test Connection does: each time the tab is opened, and again for each database expanded (through an SSH tunnel or a new AWS SSM session each time), running the startup script, read-only (a SQLite or DuckDB file that isn't there fails instead of being created), and closing the connection after. Nothing is saved until **OK**, which saves the choice with the data source. While it connects it shows the elapsed time, and **Cancel Listing** (or Esc) stops it; when it fails, the error shows with **Try Again**, which uses the dialog's settings as they are then (a server without TLS offers **Allow unencrypted for this data source** there too; for an unknown SSH host key or a missing driver, use Test Connection first). A saved data source lists through its saved settings. Later, right-click › **Manage Shown Schemas…** changes the same choice; the TUI's data source form has no Schemas tab, so the TUI chooses there (`s`).
- **Production**: before a statement that changes data runs, Qurry counts the rows it will change (the same table and WHERE as a `SELECT count(*)`, nothing is changed) and asks. Statements it can't count (`UPDATE … FROM`, `DELETE … USING`, CTEs) still ask; statements that change the structure (DDL) show as "schema change". Reads run without asking, also when a write word appears only in a string or a comment (`select 'delete' as action`, MySQL `# delete …`); a quoted name such as `"update"` still asks. With a backslash in a string, where the string ends depends on a server setting (MySQL `NO_BACKSLASH_ESCAPES` and `ANSI_QUOTES`, PostgreSQL `standard_conforming_strings`), so Qurry asks if the statement would change data under any of them. A call to a function with side effects (`dblink_exec`, `setval`, `set_config`, `pg_sleep`, MySQL `get_lock` …) also asks, since the write can be hidden in a string it runs, and so do sequence and large-object writers (`nextval`, `lo_unlink` …) and `SELECT … INTO` (a new table, a file on the MySQL server, or MySQL `@variables`). A selection run as one statement (Query Execution Settings › For selection execute › Exactly as a single statement) goes to the server as one text, so it asks if any statement in it changes data (`select 1; do $$ … delete … $$`, MySQL `select 1; prepare s from '…'; execute s`). The GUI and the TUI decide this the same way. GUI: Options tab · TUI: the `Production` toggle in the data source form. New PostgreSQL and MySQL consoles of a Production data source start in Tx: Manual, so a change stays pending until Commit / Roll back (a plain read before it doesn't open the transaction): turn off **Production: start consoles in Manual transaction mode** under it (TUI: `Production Manual`) to start them in the Transaction control mode instead ([Safety › Production transactions](safety.md)).
- **MCP**: what AI tools may do through `qurry-mcp` — Off (new data sources; not listed, never connected), Read, or Read & write (with `--allow-write`; not for Read-only or Production data sources). See [MCP server](mcp.md). GUI: Options tab · TUI: the `MCP` field.

> Redis Sentinel and Cluster nodes advertise their own addresses, so they can't be combined with an SSH or AWS SSM tunnel.

## Redis browser

- **Explorer**: a Redis data source lists its databases (`db0`, the configured one and every one with keys) with their key counts; the keys themselves are in the Redis tab. Double-click (TUI `Enter`) opens the data source's Redis tab on that database; a click on another database switches the open tab to it.
- **One Redis tab per data source**: its toolbar has the database picker (`db0 · 500 keys`; TUI `d`) and the key filter, a SCAN pattern such as `prod:user:*` (TUI `/`). The workspace keeps the picked database. A workspace saved before 0.3.2 with a tab per database reopens one tab on the database saved last.
- **Key tree**: keys are grouped into folders by `:`, with the folder's key count beside its name (`sessions 419`); the TTL column shows each key's TTL (`1d 4h`), `—` for a key without expiry. The value panel on the right has **Content · Terminal · Info · Config**.
- **Config** is greyed out where the server refuses `CONFIG` (managed Redis: AWS ElastiCache / MemoryDB, Azure Cache, GCP Memorystore, Upstash … disable or rename it; checked once on connect). Hover it for why: the settings are in the provider's console (e.g. the ElastiCache parameter group), and **Info** still shows the server details.
- **Terminal** (TUI `:`): typing a command lists the commands it can become, with their arguments and summary (`HG` → `HGET key field`, `HGETALL key`), from a command table bundled with Qurry; a key argument completes key names from a bounded SCAN (a key with spaces or quotes goes in quoted, as one argument). `⇥` picks, `⎋` closes the list; `↩` picks a command, but a key name only after `↑` `↓` moved to it, so `↩` on a key typed out in full (`GET user:1`) runs the line even when a longer key (`user:10`) is listed. The arguments still to type show after the text. `↑` `↓` go through this data source's history (shared with Query History; passwords in `AUTH`, `HELLO … AUTH`, `CONFIG SET requirepass` / `masterauth`, `ACL SETUSER … >password` and `MIGRATE … AUTH` are masked, quoted ones too). `HELP <command>` prints its arguments and summary. Replies show by type: a hash as a field / value table, a list numbered from 0, a set or sorted set as rows (with scores after `WITHSCORES`), nil and errors styled.
- **Same rules as the console**: a read-only data source runs read commands only (a command not in the table counts as a write), a Production data source asks before any write, and `FLUSHALL` / `FLUSHDB` / `DEL` (and other commands that delete or run scripts) always ask.

## Export and import

**Export Data Sources…** (explorer ⋮ menu, Find Action) writes every data source to a JSON file, without passwords. **Import Data Sources** reads that file back, or the data sources of DataGrip / IntelliJ IDEA and DBeaver:

- **GUI**: explorer ⋮ (or **+**) › **Import Data Sources ▸** (an empty explorer has an *Import data sources…* link too) lists the locations found on this computer, newest IDE version first, each with how many data sources it has (the path is the tooltip). Below them, **File…** and **Folder…** open the system picker (it picks a file or a folder, not both). Find Action (`⇧⌘A`) lists the same as *Import Data Sources: …*.
- **TUI**: `⌃k` › **Import Data Sources…** lists the same locations, then **File or folder…**, which asks for a path (`~` is your home folder).

The format is detected from what you pick: a Qurry export; `dataSources.xml` or `dataSources.local.xml`; a project folder or its `.idea`; an IDE options folder; DBeaver's `data-sources.json` (or `data-sources-*.json`); a `.dbeaver` folder, a DBeaver project or its workspace folder. A folder with `qurry-datasources.json` in it reads that export.

Then the import confirm shows one row per data source: what is added (name, server), what was mapped (type, SSH tunnel, SSL, Read-only, Production), and on the right *password on connect*, *no password* (DataGrip's No auth) or a warning such as *SSL without certificate checks*. Every added row has a checkbox (checked): uncheck the ones to leave out; **Import N** (TUI: `y` / `Enter`) imports the checked ones and is disabled at 0. TUI: `↑` `↓` move, `Space` checks, `n` / `Esc` cancel. Rows that can't be imported are listed with the reason and have no checkbox: a kind Qurry doesn't support (Snowflake, BigQuery, Db2, CSV files …), or one Qurry already has (same type, server, user and database). When nothing can be imported, a notice lists the rows instead. A file that can't be read says where (line and column) and nothing is imported.

New data sources get fresh ids and start with MCP Off. **Passwords are never imported**, even when a file has one: each data source asks on its first connect. Nothing is written to the other tools' folders.

Where Qurry looks (read only):

| Tool | macOS | Linux | Files read |
|---|---|---|---|
| DataGrip / IntelliJ (global) | `~/Library/Application Support/JetBrains/<IDE><version>/options` | `~/.config/JetBrains/<IDE><version>/options` | `dataSources.xml`, `dataSources.local.xml`, `sshConfigs.xml` |
| DataGrip projects | `<IDE config>/projects/<name>/.idea`, `~/DataGripProjects/<name>/.idea` | the same | `.idea/dataSources.xml`, `.idea/dataSources.local.xml`, `.idea/sshConfigs.xml` (and the IDEs' `sshConfigs.xml`) |
| Recent IDE projects | the projects in `<IDE config>/options/recentProjects.xml` that have an `.idea/dataSources.xml` | the same | as above |
| DBeaver | `~/Library/DBeaverData/workspace6/<project>/.dbeaver` | `~/.local/share/DBeaverData/workspace6/…`, Flatpak `~/.var/app/io.dbeaver.DBeaverCommunity/data/DBeaverData/workspace6/…`, Snap `~/snap/dbeaver-ce/current/.local/share/DBeaverData/workspace6/…` | `data-sources.json`, `data-sources-*.json` |

What is mapped:

| | DataGrip / IntelliJ | DBeaver |
|---|---|---|
| Type, host, port, database | from the JDBC URL: PostgreSQL, MySQL / MariaDB, SQL Server, Oracle (`@//host:port/service`; `host:port:SID` uses the SID as the service name, with a warning), ClickHouse, Redis, MongoDB (`mongodb+srv://` as the host), SQLite / DuckDB (the file). URL parameters are dropped | the connection's host, port and database (the URL when they're missing) |
| User | `user-name` | `configuration.user` when the file has it; DBeaver usually keeps it with the password (`credentials-config.json`, never read), so the row warns and you enter it |
| SSH tunnel | the SSH configuration it refers to (`sshConfigs.xml`: host, port, user, password or key file), or the older tunnel inside the data source. *OpenSSH config and agent* logs in with ssh-agent and `~/.ssh/config` | `ssh_tunnel`: host, port, user, password or key file (`${project.path}` expanded); agent: ssh-agent |
| SSL | mode (Require / Verify CA / Full Verification), CA, client certificate and key | `*_ssl` handlers: `sslMode` (disable leaves SSL off), CA, client certificate and key; MySQL *Verify server certificate* = Verify CA |
| Read-only | `read-only="true"` | `read-only` |
| Production | — | connection type *Production* (`prod`) |

Not imported: passwords and SSH passphrases, driver properties and JDBC parameters, schema filters, colors, folders, and SSH host names that only exist in `~/.ssh/config` (the tunnel takes the host DataGrip stores).

## Drivers (added when you need them)

Nothing extra is installed up front. Pick one of these types for a data source and Qurry offers to **Install** its driver: a small program downloaded from the GitHub release of your Qurry version, checked against the signed `SHA256SUMS` (same key as app updates) and kept in the config folder under `drivers/`.

| Database | Notes |
|---|---|
| SQL Server | SQL Server 2017+ (older versions work, with a warning); `dbo` and other schemas |
| Oracle | Needs the free [Oracle Instant Client](https://www.oracle.com/database/technologies/instant-client.html) — set its folder in the data source (or `ORACLE_CLIENT_LIB_DIR`). Oracle 19c+ (11g works, with a warning); the service name goes in Database |
| SQLite · DuckDB | A file instead of host and port (DuckDB: empty = in memory) |
| ClickHouse | Over HTTP (port 8123) |
| MongoDB | Shell syntax in the console: `db.users.find({age: {$gt: 30}}).sort({age: -1}).limit(10)`, `aggregate`, `countDocuments`, `insertMany`, `updateMany` …, or a command as JSON. Fields are guessed from 50 documents |
| Qdrant · Chroma · Milvus | Collections are tables. The console takes REST requests — see [Vector databases](vector-and-rag.md) |

The data source test shows the server version and warns when it is older than the versions Qurry is tested with (PostgreSQL 12, MySQL 5.7, MariaDB 10.5, SQL Server 2017, MongoDB 5, ClickHouse 22, Oracle 19c — CI runs against these). Read-only data sources are enforced for drivers too: MongoDB runs only `find` / `aggregate` (without `$out` / `$merge`) / `count` / `distinct`, vector databases only `GET` and search requests.

Each data source can have a color that tints its tree and marks its tabs (handy for telling production apart). Besides the presets, the rainbow swatch opens the system color picker — on macOS its eyedropper picks any pixel on screen, e.g. the color you used in DataGrip — or type a hex value next to it. The TUI cycles through the presets and keeps a custom color as is.

The active tab stands out: it takes the editor's background (a colored data source's tab its full color), bold text and an accent bar (gray in a split pane that doesn't have focus); the other tabs keep the stripe and a fainter tint. Tabs, the Switcher, Recent Files and Search Everywhere show the same icon as the object's row in the explorer, and a DDL tab adds a small DDL mark to its object's icon (a DDL tab saved by an older version shows the generic DDL icon until it is reopened). The TUI uses the tree's glyphs in the tab bar, Recent Tabs (`⌃e`) and the `⌃p` search, with `≡` after a DDL tab's glyph; for how its active tab looks, see [TUI in your terminal](tui.md#colors).
