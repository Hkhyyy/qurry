- **[medium] GO verdict has no evidence for the oldest supported WebViews**
  - Where: src-tauri/tauri.conf.json:24 (CSP), scripts/perf/wasm-smoke.mjs:9-11, src/main.tsx:12-13

- **[medium] A COMMIT cut off by a lost connection is logged as 'ROLLBACK (by the server)', but it may have committed**
  - Where: crates/core/src/session.rs:133-140 (PgSession::commit sets in_tx=false on any error) + crates/core/src/app.rs:901-916 (commit_tx -> audit_lost_tx at :912, defined at :811)
  - Scenario: Production PG source, Manual console with a logged DELETE. PgSession::commit now sets in_tx=false on every error, so tx_state() returns false and audit_lost_tx writes 'ROLLBACK (by the server)' after the failed COMMIT entry. Now: the Production log says the change was rolled back, so a user who trusts it may run the DELETE/UPDATE again on prod. Expected: the outcome is logged as unknown.   - Fix: In audit_lost_tx / commit_tx, log 'ROLLBACK (by the server)' only when the error is AppError::Db(sqlx::Error::Database(_)). If is_conn_lost(e), write 'COMMIT outcome unknown (connection lost)', or leave the entry as started/'no result recorded'. Add a unit test with an Io error. Breaks nobody.
