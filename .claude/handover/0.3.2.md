# 0.3.2 handover

For a session (any machine) that picks up the 0.3.2 batch. Read all of it before starting. Remove `.claude/handover/` from the branch before the PR (the repo is public).

## Talking to the user

- Reply in Korean, casual 반말, every message including short progress notes and the final report.
- Everything written into the repo is English: commits (`[feat]` / `[fix]` / `[docs]` / `[test]` / `[chore]` …), code comments, test names, PR title and body, UI strings. The only Korean is the user guide `docs/ko/`; `docs/<x>.md` and `docs/ko/<x>.md` change together.
- Shortcuts are written ⌘ ⌥ ⌃ ⇧ (`⇧⌘L`, `⌃k`), never "Ctrl+" / "Alt+", in docs, UI text and replies.
- No Co-Authored-By. Stage files explicitly (no `git add -A`); screenshots and scratch files never go into commits.
- Ask before outward actions the user hasn't asked for (issue edits, releases). Weekly usage limit: pause when it nears 90%.

## Release model

- One PR per batch: all of 0.3.2 goes on `feature/issues-0.3.2`, one PR at the end. If a PR is open, add to it instead of opening another.
- Never merge to main: the user merges. Every main merge publishes a beta; a stable release only comes from a `v*` tag, which the user decides (stable tags are admin-only by a ruleset).
- `Closes` lines: one per issue ("Closes #103" on its own line). A single-line `Closes #a #b` closed only the first one in 0.3.1.

## Harness

- Agents: `.claude/agents/` (qurry-lead, qurry-security, qurry-ui, qurry-perf). Workflow: `.claude/workflows/qurry-batch.js`, run with `Workflow({ scriptPath, args: { request, repo, base, batch, items?, parallel?, fixRounds? } })`. `args.repo` is required.
- Flow: Plan (lead) → Build each item on its own branch in a worktree → Review → Fix → Integrate (lead merges into the batch branch, full verification, push; never merges to main).
- Token budget (the user chose this): ONE reviewer per item (the owner's lens plus correctness and design); more lenses (`lenses: [...]`) only for big or risky items. Small, well-scoped work is one agent plus one reviewer, or a harness item with `small: true`. Skeptic verification only for medium / high findings.
- Fix comprehensively: when fixing a bug, sweep the sibling and parent cases in the same pass (the user asked for this after a fix missed the database level of the same toggle).
- Keep the main checkout clean: agents have switched it to their branches before; work in worktrees.

## Engineering principles

YAGNI, KISS, DRY. Surgical changes; match the surrounding code. Tests for what changes (core unit tests, GUI e2e with Playwright on the `?mock` backend, TUI characterization / snapshots). GUI and TUI behave the same unless an option says otherwise.

## Machine-specific (set these up for the machine you're on)

The rules below were for the original Mac; keep their intent:
- Don't use ports the user has DB tunnels on (ask which); check a port is free before binding.
- Touch only `qurry-demo-*` docker containers.
- Never touch the user's real Qurry config folder; use a scratch `--config-dir` or the beta app identifier `com.hyunkyo.dbtool.beta`.
- Don't automate the GUI while the user's Qurry app is running.
- GitHub: writes to this repo go as the repo owner (Hkhyyy). If another `gh` account is active, use `GH_TOKEN=$(gh auth token -u Hkhyyy) gh …` per command rather than switching globally.
- A shared `CARGO_TARGET_DIR` across worktrees can pick up another worktree's build: touch the .rs files before building, or use one target dir per worktree.
